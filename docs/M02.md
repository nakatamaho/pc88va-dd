# M02: graphics bring-up

## Current live candidate

[Live integration and hardware handoff](LIVE-M02.md) now connects packed
G0/G1 rendering to the three-program scheduler, with a staged graphics loader,
first-use cache generation and queued VRTC presentation. A primary run reached
3000 updates / 6297 scheduler frames; twelve sampled live states matched host
composition. CALLN native-entry CLI guards fixed a long-run race; all four
M01 probes pass for both explicit revisions. VA/VA2 and combined-speed/pacing
acceptance remain open; M02 is not marked complete. The sections below retain
the earlier graphics/snapshot baselines.

## Format and memory

The BNN technical manual, chapter 4, section 2.3 (printed page 86),
describes indexed 8bpp: the low five bits select one of 32 palette entries,
each chosen from 4096 RGB colours. Port 010Ch selects palette mode 3
(PLTM2..0 = 111). This is distinct from direct-colour 8bpp.

Use graphics screen 0 alone, 320x224 at 15.98 kHz. Centre the 288x224
board raster with 16-dot margins, without rotation or colour reduction.
RGB values are quantized to four bits per channel.

Each page is 71680 bytes (70 KiB). Three fit in 256 KiB GVRAM at offsets
00000h, 11800h and 23000h, leaving 46 KiB. The native probe currently uses
page 0 for composition and page 1 for the sprite-free background/character
cache. Page 2 is reserved for a future alternating display buffer. These
are memory areas, not three hardware graphics screens. The optional native
SGP backend uses the remaining 46 KiB for retained sprite images.

A separate [two-screen probe](TWO-PLANES.md) now verifies a packed-4bpp
background plus two alternating front pages, with separate palette banks.
Two-screen mode splits GVRAM into fixed 128 KiB regions: two 8bpp front
pages would not fit one region despite fitting in the total 256 KiB.
The validated 4bpp layout uses 105 KiB for all three images, preserving
background colours and opaque sprite colours. An optional
[native packed compositor](NATIVE-PLANES.md) now implements background updates,
page-local front damage and VRTC swaps. Its 60-transition rendering sum is
about 5.3% lower than the 8bpp SGP reference, but the first-back-page peak
is higher. Live integration remains pending; both backends are retained.
A [packed-source SGP probe](PACKED-SGP.md) verifies first-use conversion,
512 keys in 64 KiB, clipped nibble transfers and opposite-Y cache reuse on
both front pages. The newer native compositor also verifies page-local
clearing, both independent planes and the final rendered RGB image.

## Host reference

`tools/gfx.py` decodes source pens. `tools/render.py SNAPSHOT --roms PATH`
composes a 64 KiB main-address snapshot into `build/gfx/frame.indices`
(288x224) and an index-only PGM. Video latches must be at A000h..A007h.
Local flips, large sprites, wrapping, clipping, colour lookup and
foreground transparency are implemented. Global screen flip is rejected.

`tools/check_screen.py --roms PATH --mame EXE --system SET --rompath DIR`
compares host composition with reference-emulator RGB, using its palette.
Captures read only video RAM windows, never I/O, and zero unused addresses.
Writes to the video latches are observed on all three CPU buses. In the
tested reference build, screen:pixels() exposes the previous bitmap after
the callback's buffer swap; it is paired explicitly with previous RAM.

Both revisions passed 200 samples (every 30 frames over 6000) with no
pixel differences. Primary-revision frames 1200-1260 also passed every
frame (`--first-frame 1200 --frames 1260 --period 1`). Input includes coin,
start, directions and button presses. This is not every scene or round.
The primary assets are from the user's re-release; graphics are shared
between revisions. Outputs stay under ignored build/.

## Native probes

```
python3 -I tools/build_screen.py
python3 -I tools/build_screen.py --pages --output build/m02pages.d88
python3 -I tools/build_screen.py --native --snapshot CAPTURE.memory --roms PATH --output build/m02native.d88
```

- Default: ROM-free colour bars, outer border and eight-line ruler.
- `--pages`: copy to three pages and cycle DSA every 60 VRTCs; two pixels
  distinguish pages 1 and 2.
- `--snapshot` without `--native`: host-composed static image.
- `--native`: V30 code expands RLE source pens into main RAM and composes
  frozen video state. It does not run the game.
- Repeated `--next-snapshot NEXT.memory` arguments replay following states
  on the same image/shadow. The single-segment boot payload limits the
  number of states; byte-delta encoding now fits all 60 consecutive test
  transitions in one run.
- `--native-sgp`: retained SGP sprites within the same native compositor;
  see [NATIVE-SGP.md](NATIVE-SGP.md) for allocation, fallback and tests.

Set the monitor to 15 kHz before boot; 24 kHz prints a refusal message.
The probes use the established 37/224/2/4 SYNC vector, word framebuffer
register writes and single-plane CPU GVRAM writes. Reset to leave.

Native allocation: source character/background pens at 3000:0000..7FFF,
sprites at 4000:0000..FFFF, video-state shadow at 3800:0000. The SGP
backend uses 7000:0000..FFFF plus the GVRAM tail, without touching the
5000/6000 Z80 banks or requiring expansion RAM. Live code/payload loading
still needs integration. No MCU dumps enter builds.

## Incremental composition

Unchanged state returns after a word comparison. Changed character cells
are decoded and written to both the output and the sprite-free cache.
For a changed sprite, mark the old and new clipped/wrapped footprints in
an 8x8-cell damage map, including size changes, appearance and disappearance.
Restore unchanged character cells in those footprints from cached GVRAM,
then redraw intersecting sprites in original order. Sprite writes are
masked to damage cells, preserving priority outside the restored region.
An inverse RAM-to-row map also skips untouched rows when character RAM
changes, continuing word comparisons through matching spans. Video-latch changes
still trigger a complete redraw/cache rebuild.

This probe still updates one output page without synchronized animation.
Cache restoration and incremental correctness are not live-game support.

## Tests and measurements

```
python3 -I tools/test_gfx.py
python3 -I tools/test_render.py
python3 -I tools/test_screen.py
python3 -I tools/test_video_cases.py
python3 -I tools/check_pages.py --vaeg EXE --bios DIR
python3 -I tools/video_cases.py CAPTURE.memory
python3 -I tools/check_native.py --vaeg EXE --bios DIR --roms PATH FIRST.memory --next-snapshot SECOND.memory
```

- 51 ROM-free unit tests passed (including the SGP experiments).
- Static images matched all 71680 expected GVRAM bytes; screenshots showed
  bars and the primary-asset scene. Maintainer screenshots independently
  confirm vaeg presentation, not hardware or sustained page cycling.
- Three-page probe matched all 215040 bytes, including markers. It checks
  registers at consecutive display switches to reject skipped events.
- All 60 consecutive primary-state transitions from frame 1200 to 1260
  matched host output with both backends, each in one retained run. Nine mixed
  synthetic transitions also matched: movement, wrapping, clipping,
  size/colour/flip changes, disappearance/appearance, overlapping cells,
  latch changes and unchanged state.
- Typical measured unchanged update: 6512 guest clocks (~0.049 frames).
  A six-cell sprite movement in the sampled interval: about 119000 clocks
  (~0.89 frames). Updates that also change character RAM reached about
  209000 clocks (~1.57 frames) in the original CPU baseline. Row scanning
  and the integrated SGP backend now reduce the sampled maximum to
  102512 clocks (~0.77 frames); see [current timings](NATIVE-SGP.md).
  Larger synthetic changes cost more.
- Full-page REP MOVSW: 334100 guest clocks, **2.503 display frames**.
  Initial full composition plus cache construction takes millions of
  clocks and is unsuitable for every-frame use.
- Palette quantization matched all 32 reference entries converted to VA
  palette words. M01 still builds for both revisions, with unchanged runtime.

Timing correction: earlier notes reported 0.834 frames for the full-page
copy and similarly optimistic incremental frame fractions. The harness
arms each wait-pc separately; ordinal 2/3 skipped future occurrences
rather than selecting cumulative occurrences. The reference interval
therefore covered three page periods. Corrected scripts use ordinal 1
for each next event and validate page identities. Raw clock counts were
unaffected; prior frame fractions must not be used. About 133460 guest
clocks per display frame were measured from consecutive page switches.

These measurements exclude the concurrent three-program scheduler and
are not hardware timing or acceptance. Native checks capture GVRAM before
final display timing; separate static probes check presentation.

## SGP experiment

A separate synthetic 8bpp benchmark compares CPU restoration/painting
with SGP command-list construction, restoration, transparent blits and
busy wait. All eight workloads matched independent expected images;
SGP was 2.2-3.0 times faster in the tested emulator. Source preparation
and the game scheduler are excluded. See [SGP benchmark](SGP-BENCH.md)
for reproducible commands, exact costs and timing-model limitations.
The [follow-up evaluation](SGP-CACHE.md) measures real-source palette/X-flip
conversion and cache lookup/replacement. Y flip uses SGP negative pitch.
Warm caches can win substantially, but cold conversion and conflicts can
lose to CPU. The [retained-cache extension](CACHE-WARMUP.md) traces all
6000 reference frames: 341 unique keys (85.25 KiB), 281 before scripted
start. A 512-slot no-eviction guest probe retains the complete first-use
manifest with matching pixels and directory counts. The newer
[integrated native backend](NATIVE-SGP.md) keeps 440 slots using standard
RAM and the spare GVRAM tail, with CPU fallback on capacity exhaustion.
Its 59-state integration test retains all 341 observed keys and preserves
both Z80 banks and the reserved third page. This is still snapshot replay,
not live execution of the three game programs.
