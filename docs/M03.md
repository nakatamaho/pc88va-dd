# M03: SSG first, two FM calculation paths

> Since M03 every game disk is an MS-DOS 4.0 disk with DD.COM, which loads
> DDGAME.DAT and FMVOICE.DAT to the same memory as described here
> (`docs/DIST.md`, AGENTS.md "Making disks"). Mentions of the IPL loading
> game disks below are historical; `build_live.py` now writes MS-DOS disks.

M02 hardware acceptance is deferred by the maintainer. It remains open,
not passed. Work continues on `topic/m03-sound`; the silent M02 build and
its graphics/protocol tests remain available as references.

## Modes

| Mode | Role | Tone generation | Where expensive work happens |
|---|---|---|---|
| `ssg` | Primary/default M03 backend | Three SSG square tones | Small native integer conversion only |
| `fm-lite` | Auxiliary low-cost approximation | Four independent sine carriers, strongest source harmonics | Fast host DFT plus approximate native pitch arithmetic |
| `fm-fit` | Auxiliary detailed calculation | Fitted four-operator low/high profiles | Expensive host-side nonlinear search; native uses generated profiles and exact pitch arithmetic |

The heavy search **does not run on the VA CPU**. It is deliberately separated
from per-update native work because the live renderer already has a tight
budget. FM-fit can still issue more OPN writes when changing pitch ranges.
These are separate build-time modes/disks; there is no runtime sound menu yet.
The BSD-2-Clause sister project's sound design and offline fitter are the
reference; the copied fitter retains its original copyright/license notice.

## Register protocol and timing

The existing sound Z80 program runs twice per scheduler frame via NMI.
Its 6800h..681Fh sound-register window is already copied back into shared
RAM by the scheduler. After sound-program yield or preemption, snapshot
those 32 bytes and update the native sound backend. No dump of a custom
I/O microcontroller is used.

Three voices use waveform registers 05h/0Ah/0Fh, frequency nibbles ending
at 14h/19h/1Eh and volumes 15h/1Ah/1Fh. Voice 0 has all 20 frequency bits;
voices 1/2 have 16 nibbled bits shifted left four. Only low register nibbles
are significant; waveform selection uses three bits. The reference driver
configures the WSG input at 96 kHz. Its 32 held samples form a waveform
whose fundamental is `96000 * F / 2^20`.

The YM2203 uses ports 44h/45h, initialized to its 1/6 prescaler. The SSG
clock is 998400 Hz for the 3.9936 MHz OPN source. Preserve the SSG mixer
I/O-port direction bits; never write its port A/B data. All unused sound
channels are silenced on initialization. Native updates run with the
scheduler's CALLN/preemption interrupt guards active. They preserve all
context registers and return to the established native stack flow.

OPN writes wait for busy with a bounded 4096-poll loop. A timeout sets a
sticky error and disables further audio writes, rather than hanging the
game in an unbounded poll. Register writes are suppressed when the requested
period/level/profile/key has not changed. Tests explicitly require zero
writes on an identical repeated request. This does not suppress decoding
or all pitch calculations; those costs remain in the measurements.

## SSG approximation

`TP = clamp(floor(681574 / F), 1, 4095)`. Zero frequency or volume silences
the voice. An integer linear-volume to logarithmic-SSG-level table controls
amplitude. No SSG envelope/noise generator is used. Source waveform shape,
phase, sample-hold buzz and exact amplitude are **not** reproduced by square
tones. This is the primary lightweight baseline, not audio-identical output.

The native 20-bit division is exact for this integer numerator: 16-bit DIV
handles smaller F, while at most ten 20-bit subtractions handle large F.
`tools/check_sound_math.py` executes all 1048575 nonzero inputs and compares
32-bit sum/16-bit XOR with independent host arithmetic. It completed with
matching aggregates. This is exhaustive input execution with checksum
comparison, not individual logging of a million values.

## FM-lite

`tools/fmvoice.py` analyzes each 32-sample waveform's harmonics 1..15,
including the sample-hold sinc factor. Select four strongest magnitudes,
use algorithm 7/no feedback, map harmonic numbers to operator multipliers
and magnitudes to total levels. Normalize the carrier-amplitude sum so the
model's peak bound is at most one full-scale carrier. Phase is discarded.
The same profile is used at low/high pitch to avoid range-switch reloads.
No iterative optimization or NumPy dependency is needed for this path.

Native pitch approximates `F * 45 / 13` by `F * 443 / 128` and packs block/
F-number. The native routine uses two word multiplications plus shifts.
As in the sister implementation, out-of-range FM pitch saturates at block
7/F-number 2047 rather than overflowing. Upper original pitches therefore
cannot all be represented. Multipliers extend individual partials, not the
fundamental conversion's saturation range.

## FM-fit

`tools/fmfit.py` models four-operator modulation and feedback and searches
algorithms, feedback levels, multipliers and total levels. Each source
waveform gets a LOW/HIGH profile. Below 576 Hz (F < 6292), the target includes
sample-hold images through harmonic 48; above, it uses harmonics through 16
to reduce modeled high-frequency aliasing. The search uses deterministic
seeds. Its spectral distance discards phase and minimizes relative harmonic
power error; carrier levels are normalized for RMS/peak constraints.

Native pitch uses exact integer `F * 45 / 13`, with two safe DIV steps for
the double-word numerator. The same block/F-number limits apply. Algorithms,
operator multipliers/levels and carrier attenuation come from the generated
profile. Envelopes are flat, with key-on held while the source voice is
active. Source volume changes carrier TL, not the modulators' base TL.
Profiles change only when waveform/range changes; pitches, levels and keys
are written only when needed.

Fitted waveforms and final sound are approximations: the host model is not
physical YM2203 measurement or guaranteed bit-exact emulation. Phase continuity,
quantization, carrier clipping, aliasing and perceived timbre require listening.
Do not equate the optimization score with audio-quality acceptance.

Both pitch routines completed the same exhaustive nonzero 20-bit checksum
test as SSG. No divide exception or wrap was observed.

## Host build cost and private assets

For the user's primary waveforms on this development host, a fresh light
analysis took about 0.003 seconds; a fresh fitted search took about 16 seconds
for all 16 LOW/HIGH jobs. These are machine-dependent measurements, not build
time guarantees. A version/mode/source-hash cache under `build/fm-cache/`
avoids repeating the expensive fit. Each mode produces only 144 profile bytes
for runtime use, loaded with the existing transient graphics/tables payload.
NumPy is required only for FM-fit and its model analysis.

On the fitter's own model, mean spectral cost over the 16 targets was about
287.5 for the additive approximation and 28.5 for fitted profiles. Units are
weighted squared log-spectral error, **not** a measured loudness or a tenfold
perceived improvement. Neither is a comparison with recorded hardware audio.

The source waveform PROM, profile binaries, caches, reports, disks and captures
are private user-asset derivatives under ignored build/. None are committed.

## Native verification and cost

`tools/check_sound.py` sends identical synthetic control sequences to all
three native backends, with user-derived FM profiles where supplied. It
checks 58 exported target states per mode: all eight wave selections, both
pitch ranges, zero/low/full volume, 16/20-bit pitch boundaries, saturation,
key-off and immediate identical repeats. The test includes simultaneous
three-voice changes. No game program is needed by this synthetic probe.

The exports are **shadows of values sent through OUT**, not chip readback or
PCM analysis. Tests validate decoding, arithmetic, profile/operator mapping,
key state and register suppression. Actual synthesis/analog output is still
a listening/hardware gate. Busy timeout did not occur in the healthy tests.

| Mode | Changed-request clocks | Identical-repeat clocks | Changed writes | Repeat writes |
|---|---:|---:|---:|---:|
| SSG | 1408-3652 | 1197-2571 | 0-9 | 0 |
| FM-lite | 1875-12493 | 1228-3010 | 0-36 | 0 |
| FM-fit | 1876-12249 | 1239-2848 | 0-36 | 0 |

These are guest clocks per **three-voice update**, including source-window
snapshot, decode/conversion, shadow comparisons, writes and busy wait.
Initialization, probe input copying and diagnostic export are excluded.
They are synthetic request ranges, not whole-frame maxima or hardware timing.
Normally two sound NMIs occur per scheduler frame, but preemptions can add
partial-state updates; do not assume exactly two calls in every scenario.

FM-fit is not universally slower on the target: its exact arithmetic can be
cheaper than the light shift loop. The expensive distinction is primarily
offline fitting and additional profile traffic. In the first LOW->HIGH test,
FM-lite needed six writes / 4111 clocks; FM-fit needed 33 / 11711. Source
wave/range changes, not just division, determine target cost.

## Load reduction experiments (opt-in, in progress)

Maintainer listening in vaeg reported slow tempo and dropouts in both SSG
and FM-fit, worse with many characters, plus slowdown at stage start. These
point to combined game/render load delaying the sound program, not to timbre.
The following are opt-in `build_live.py`/`check_live.py` flags; defaults are
unchanged, and the silent M02 disk rebuilds to the identical hash.

- Unchanged sound window (all audio modes, default): compare the 32-byte
  window and return before decoding. Identical repeats drop from about
  1200-2900 to 270 guest clocks with zero OPN writes.
- `--background-cache`: no-eviction cache of composited packed 8x8
  background/character tiles, 2048 slots in GVRAM 29200h..391FFh (first
  28C00h; moved for the alignment margins) with tag
  directories in reclaimed CS 9000h..EFFFh. Empty glyphs share one key;
  uniform-colour background lookups ignore the map code. Full first
  composition dropped from about 3.41 million to 0.96 million clocks.
  Diagnostic exports move to 12400h (first 11800h) to stay clear of the cache.
- `--coalesce`: when every damage cell under a clipped sprite piece is dirty,
  issue one transfer instead of up to nine per-cell fragments. The mixed
  fixture movement dropped from about 520k to 418k clocks; the consecutive
  60-transition sum dropped from 1.80M to 1.67M.
- `--sound-priority`: run a pending sound NMI before other CPUs. Delivered
  and dropped NMI counts are exported for comparison. Effect on audible
  tempo is not yet evaluated.

All combinations tested pass consecutive snapshot pixels/RGB, capacity-1
fallback, live sampled composition, independent background planes, sound
register targets and memory guards. Live samples with all flags reached
1500 updates for SSG and FM-fit.

`tools/profile_native.py` splits the mixed movement fixture by guest PC
(cold = 15 first-use conversions, warm = all keys cached; 24 pieces, 183
cleared 8x8 cells, same pixels):

| Part | Cold clocks | Warm clocks |
|---|---:|---:|
| Clear reused front cells (CPU) | 107487 | 107487 |
| Damage/scan/clipping and other native work | 110148 | 110157 |
| Cache lookup and first-use conversion | 150492 | 10785 |
| SGP list construction | 15343 | 15343 |
| SGP submit and completion wait | 34645 | 34645 |
| Total | 418115 | 278417 |

### Front clearing policies

`tools/compare_clear.py` runs identical inputs through every policy; each
run must pass check_native's pixel, final-RGB and memory-guard checks.
"Mixed" is the fixture above (cold first-use and a warm second pass);
"60" is the consecutive primary sequence (frames 1201-1260).

| Policy | Mixed cold | Mixed warm | 60 sum | 60 max |
|---|---:|---:|---:|---:|
| Per-cell CPU clear (previous) | 418345 | 278659 | 1673688 | 118125 |
| Merged CPU runs (`--cpu-run-clear`) | 364773 | 225000 | 1622925 | 118123 |
| Whole front by SGP CLS, one batch list (`--front-full`) | 309419 | 169624 | 2990368 | 170566 |
| Whole front by CPU, one batch list (comparison) | 310823 | 171033 | 3083017 | 180636 |
| Hybrid, threshold 16 (`--front-hybrid --coalesce`) | 309750 | 169960 | 1666727 | 107384 |

Findings:

- Whole-front clearing wins for large changes but nearly doubles the cost
  of small moves, because every visible piece is redrawn. This matches the
  maintainer's earlier observation that SGP dirty rectangles were slow:
  bookkeeping, not transfer, dominated.
- SGP CLS and a CPU fill of the whole front cost almost the same in vaeg.
  Its model charges the CPU four clocks for every SGP memory access, so the
  asynchronous clear gives little benefit here. Hardware contention is not
  modeled exactly and may differ.
- Building the damage map alone cost about 55k clocks on the mixed case.
  The hybrid therefore decides first with a cheap count: 16x16 pieces of
  entries that differ from this front's previous state (old plus new, large
  objects count four). At or above the threshold, skip the damage map, CLS
  the front and batch every piece in one list; otherwise use merged CPU runs.
  A never-drawn front is already transparent and is not cleared.
  Thresholds 8, 16 and 24 measured the same on these inputs.

CLS takes a start address and word count; whether hardware interprets the
count as N or N-1 is not measured. The first and last words of each front
are always transparent margin, so either interpretation leaves the other
front intact. The batch list lives at 3A000h..3FFFFh and the CLS list at
39B00h. A capacity fallback flushes the pending list first, preserving
priority order; fixtures pass at cache capacity 1 for both whole-front
policies.

Live, SSG with background cache, coalescing and hybrid reached 3000 updates
/ scheduler frame 6298 with all eleven sampled states matching. Diagnostic
lost VRTCs at that point: 77, against 242 for the earlier default diagnostic
run at the same frame. Late (preempted) scheduler frames stay high (1185),
so game-CPU load remains. `build_m03.py` now enables the background cache,
coalescing and hybrid policy by default; each has a `--no-...` form.

Shared routines changed (list submission split from waiting; a damage-cell
counter), so the silent M02 disk no longer rebuilds to the earlier hash.
Its default behavior was re-verified instead: 60 consecutive transitions,
mixed fixtures at capacities 512 and 1, a live run to 1500 updates and the
four M01 probes all pass.

### Per-routine profile and scan reductions

`tools/trace_profile.py` uses a trace-enabled vaeg build to attribute every
instruction's consumed clocks in one render to its enclosing global label.
On the warm mixed whole-front case it attributed about 82k instruction clocks
of the roughly 170k measured; the remainder is the emulator's per-access CPU
charge for SGP memory traffic, which is not attributed to any instruction.
Before the changes below: sprite-entry loop 24.8k, SGP wait 14.1k, state
comparison 12.9k, per-piece culling 10.7k, list emission 6.3k.

- Reject sprite entries wholly above the raster before splitting them into
  pieces and wraps; unused entries sit there. This is shared with the 8bpp
  paths. Entry loop 24.8k -> 14.5k, culling 10.7k -> 4.4k.
- Packed path: the first full-state REPE CMPSW already shows whether
  character RAM changed. Resume the character-row marking from that point
  instead of comparing character RAM again, and stop clearing the old
  global damage map, which this path rebuilds per front. State comparison
  12.9k -> 6.8k.

| Same inputs, hybrid threshold 16 | Mixed cold | Mixed warm | 60 sum | 60 max |
|---|---:|---:|---:|---:|
| Hybrid before scan reductions | 309750 | 169960 | 1666727 | 107384 |
| Hybrid after | 286825 | 147112 | 1388599 | 89874 |
| Original per-cell policy, before all of this | 418345 | 278659 | 1673688 | 118125 |

Regression after these changes: 8bpp CPU, 8bpp SGP, packed default,
hybrid and whole-front builds all pass the 60 consecutive transitions and
thirteen mixed transitions (capacity 1 too, where applicable). Live SSG and
FM-fit with the M03 defaults reached 3000 updates / scheduler frame 6297;

Diagnostic lost VRTCs at that frame: 62 (earlier 77; original default 242).
Late scheduler frames remain about 1140: game-CPU load is now the larger
share and the remaining work for tempo.

## Frame budget and sound tempo

Movement sound was reported slow while the picture stayed near 60 fps.
`tools/frame_budget.py` measures where a frame goes in vaeg during play
(automatic input, from guest frame 3000): an instruction trace attributes
native code by routine, and a second pass times every Z80 run with vaeg's
clock between `resume` (entering compatible mode) and `g_sched` (back in the
scheduler after a yield or VRTC preemption). The trace build records native
instructions only, hence the two passes.

Before the fix (one frame = 133460 clocks):

| Part | Clocks per frame | Share |
|---|---:|---:|
| main program (incl. 06xx/51xx/53xx handling during it) | 23552 | 17.6% |
| sub program | 10167 | 7.6% |
| sound program (incl. its register update) | 16257 | 12.2% |
| render | 25972 | 19.5% |
| scheduler, input, VRTC handler | about 7700 | about 5.8% |
| SGP waits and other unattributed native time | about 21000 | about 16% |
| idle | 29115 | 21.8% |

On average a fifth of the frame was idle, but about one frame in five had
none left, and a render could take up to 85026 clocks. The sound program
ran 1.83 times per frame instead of twice: at a new frame the scheduler
reset the sound NMI count to two, dropping one still pending, and VRTCs
during a long render brought no NMIs at all. Its tempo is its NMI count,
so sound ran at about 91% speed while 99.5% of VRTCs still produced a game
frame. Over 3000 frames of play: 5468 of 6034 sound NMIs delivered.

`SOUND_CATCHUP=N` (`--sound-catchup N`; 4 in `build_m03.py` and the
distribution) keeps the undelivered NMIs, adds two for every VRTC elapsed
(including VRTCs a long render hid from the scheduler) and caps the total
at N; the excess is counted as dropped. Same 3000 frames: 6022 of 6040
delivered (99.7%), 12 dropped, game frames per VRTC unchanged (99.3%).
Also giving the sound program priority (`--sound-priority`) changed little
(99.8%), so it stays off. With catch-up the sound program averages 2.01
runs and 24474 clocks per frame, idle about 19%. Pending NMIs are delivered
back to back after a busy frame rather than evenly spaced; the average
tempo is restored, short timing jitter remains. Emulator timing only.

## Screen changes, keys and FM default (after the first listening tests)

Reported in vaeg: a delay of the coin sound, F10 returning at once without
applying changed switches, and a wish for FM by default when fitted voices
are installed.

- Coin sound. The game requests it at the same scheduler frame as the
  reference emulator (coin key at frame 900, voices from 900; MAME: 903).
  But the coin switches the background to forced blank (video latch 3),
  which redrew all 1008 background tiles at once: about 1.1 million clocks,
  10 VRTCs during which nothing else ran, so the sound froze. Three changes:
  - `N_DRAWN` (1008 words at CS:84B8h, below the tile-cache directory)
    records what each G1 tile holds: a cache slot, `8000h|colour` for a
    uniform tile, or FFFFh. A tile already holding its content is skipped;
    a uniform tile (blank glyph over a one-colour lookup) is filled
    directly, without hashing or copying (909 of the 1008 tiles here).
  - The tile loop no longer recomputes the map page and colour bank from
    the latches for every tile.
  - Progressive background: a full or large background change marks rows
    pending. In the live game the row loop stops once the next VRTC is due
    (after at least `BG_MIN_ROWS`, 2, rows); the rest are drawn by the next
    renders, every frame while rows are pending. The sprite fronts are
    drawn as before. The coin's redraw now takes about 17 frames as a
    top-to-bottom wipe, with the game and sound running at one scheduler
    frame per VRTC throughout. Snapshot (non-live) builds still finish in
    one call. Live checks compare only the completed rows of a sample
    (`check_live.pending_rows`, exported at offset 760h).
- F10 and other keys. vaeg holds a key in its matrix for about two VRTCs;
  the scheduler read the keys once per scheduler frame, so a press during a
  long render was lost: F10 seemed not to work, or to close at once, and
  the coin key could be lost too. The VRTC handler now samples the keys at
  every VRTC (`scan_keys`, `scan_service`) and latches presses until the
  scheduler reads them. Checked with vaeg's real F10 key (headless input,
  `@key f10`) on the distribution disk: open, LIVES 3 to 5, close; the game
  restarts, its start screen shows the 5-lives table's first bonus
  (20000) and it gives four spare lives.
- FM default: with a fitted FMVOICE.DAT the game starts with FM; quick
  voices or none start with SSG. FM costs a little more: over the same
  1500 frames, game frames per VRTC 98.1% with FM-fit, 99.5% with SSG;
  sound NMIs delivered 100.0% / 99.9%. Both are better than before these
  changes (97.9% / 99.3%).

## High rounds

How the game scales, from its main program: the round counter (840Dh,
player 2 840Eh) is cleared at a game start and incremented at each round
start; every frame it is copied to 840Fh/8410h, which are capped at 15,
and the uncapped value is kept at 8627h. Difficulty settings that use
840Fh therefore stop rising at round 15. The two-digit round display wraps
(round 100 shows 0).

`--test-round N` (test builds only) presets 840Dh to N-1 whenever the game
has cleared it, so a game starts at round N; the reference emulator was
driven the same way. Both show the same round-100 maze with more enemies
than round 1. With the scripted input over 4000 reference frames, 16x16
sprite pieces on screen: round 1 mean 20.3 / max 25, round 15 19.8 / 34,
round 100 20.0 / 35.

Our port, FM-fit, M03 defaults, scheduler frames 1075-3486 of scripted
play (vaeg):

| Round | Game frames per VRTC | Worst window (~1.7 s) | 10th percentile | Median | Sound NMIs |
|---|---:|---:|---:|---:|---:|
| 1 | 97.4% | 93.5% | 94.3% | 97.1% | 99.9% (min window 98.5%) |
| 15 | 96.6% | | | | 100.0% |
| 100 | 95.9% | 85.0% | 89.1% | 99.0% | 100.0% (min window 99.0%) |

In the worst round-100 window (`frame_budget.py --start 2993`), idle time
was 4.9% of the frame. Shares: sound program Z80 runs 26.0% (2.01 runs
per frame, including catch-up and its FM register update; the update alone
6.6%), render 19.1%, main program 18.5% (0.88 runs per frame), sub 5.8%
(0.70), scheduler 6.2%. Busy stretches at high rounds therefore run at
about 85-90% speed for a second or two while the sound keeps its tempo;
most of the time the game keeps full speed.

### Load reductions after the measurement

- Sound update: only voices whose registers changed are converted and
  written (a forced update still writes all). One changed FM voice costs
  1.4-4k clocks instead of about 13k. `check_sound.py` adds states where a
  single voice changes.
- Shared-RAM copies between the programs use word moves where the length
  is even.
- The last SGP list of a render is submitted without waiting; the SGP
  finishes while the programs run. Every later SGP use waits first, the
  VRTC handler shows a queued page only when the SGP is idle, and the
  capture export waits before reading GVRAM.
- The second copy of a sprite piece 256 dots to the right is drawn only
  when the piece starts left of x=16.

With these, round 1 rose to 99.3% (worst window 96.2%) but round 100 stayed
at 95.6% (worst 87.1%). Profiling the worst window showed 35% of native
time idle: the CPU was not saturated. Frames that overran (render frames)
lost their VRTC for good while the frames between them waited.

### Making up overrun frames (`FRAME_DEBT`)

With `--frame-debt N` (`FRAME_DEBT=3` in M03 and distribution builds) the
scheduler advances `seen` by one VRTC per frame while it is at most N VRTCs
behind, so frames after an overrun start at once until the game has caught
up; beyond N the excess is dropped as before. Counters that measured
elapsed VRTCs (lost frames, sound NMI catch-up) now use `seen`, which equals
`tick` without the option. Same runs as above, scheduler frames from 1075:

| Round | Game frames per VRTC | Worst window | 10th percentile | Median | Sound NMIs (min window) |
|---|---:|---:|---:|---:|---:|
| 1 | 100.0% | 98.0% | 99.0% | 100.0% | 98.0% |
| 100 | 100.0% | 98.1% | 99.1% | 100.0% | 98.1% |

The cost is timing jitter of up to three frames (50 ms) inside a busy
stretch: the game briefly runs faster than the display to catch up.

## Native sound driver

The sound program is replaced by native code that does what its NMI does,
with its state at the same addresses (docs/SOUND-DRIVER.md). In the
round-100 worst stretch the sound cost dropped from 26.0% to about 4.5%
of a frame, and the tempo is now exactly two ticks a VRTC.

Changes:
- `rect_overlaps`: one array of rectangles, the cleared ones followed by
  each piece to be drawn as the walk passes it (at 3800:3800h, 1.5 KiB),
  tested inline with registers instead of a call per pair and a walk of
  all earlier pieces.
- `rect_piece` clips in registers; a kept piece only clears its flag (the
  rest of its record is already right). The entry loop passes unused
  entries in a tight scan and makes the key's high byte once per entry;
  drawing takes the clip from the record and the key as it is
  (`planes_sprite_keyed`).
- Opaque boxes: at start `rect_init` finds each of the 256 sprite images'
  box of nonzero pens (`r_bbox`, 1 KiB). When an entry's lookup makes pen 0
  transparent (all the game's lookups do), a piece's rectangle is its clip
  within that box (mirrored for flips): smaller clears, fewer overlaps,
  smaller SGP transfers. Blank pieces (39% of the pieces in the recorded
  states, e.g. empty quarters of large sprites) are neither listed nor
  drawn.
- The snapshot builder reserves 13 KiB for code (was 11 KiB; the rect
  build no longer fitted).

What is left in the busy stretch: the main program is the largest part
(Z80 code; only its idle loop and sprite copy are native), then the front
bookkeeping (`rect_piece`, `rect_entries`, `rect_clear_all`, about 5k
clocks each a frame) and the tile-RAM comparison of every render
(`live_video_frame`, 5.8k: 512 words compared at 7 clocks a word).

### Main program routines run natively

vaeg's instruction trace records native code only; with
`VAEG_UPD70008_TRACE=N` and `VAEG_UPD70008_TRACE_SKIP=M` it prints every
compatible-mode instruction with the remaining clock count, so the cost of
each Z80 instruction in the port follows from consecutive events. With the
call stack followed (CALL, RST, RET, IRQ entries), almost all of the main
program's work is inside its IRQ (95%). The reference emulator's trace of
the same play (debugger `trace`, round 100) gave the same hot routines.
Five small fixed loops, all in block 1000h, now run natively
(`tools/patches.py`; addresses rev1, rev2 two bytes higher):

| Routine | Work | Before (compatible mode, clocks a frame) |
|---|---|---:|
| 14FDh (2 calls) | three BCD bytes to six digit tiles, leading zeros blanked | 2111 |
| 1BADh | 8 x 4 bytes of the object table to sprite RAM (IX, IY) | 1544 |
| 1B90h | 8 x 2 bytes to sprite RAM (IX) | 859 |
| 1430h (1.4 calls) | 10 bytes of a table to 83D4h down | 813 |
| 16E3h | 8 bytes to sprite RAM (DE) | 678 |

The first instruction of each becomes a JP to a stub: CALLN to the native
copy (memory only, Z80 registers kept), then Z80 code that leaves the
registers as the routine does (LD IX/IY/HL/DE/A/B with the final values;
the routine's last ADD HL,DE for the flags; for 14FDh the last digit runs
as the original, so A, IX and the flags are its own). IY's mapping onto a
native register is still open on the hardware, so no native code relies
on it; IX = SI is confirmed. The block's sum is kept through a byte of
1B90h, no longer reached (`DEAD_FILLERS`); the power-on ROM test passes.
1430h's loop is also entered from elsewhere and stays.

Checks: the video state (tile, sprite RAM, latches) of 120 consecutive
game frames (two windows) is identical, byte for byte, to the build
before; samples every 50 frames to frame 4321 also match except for
one-frame timing phases (a moving sprite one step behind for a frame),
which appear in the same way between two builds whose programs are the
same (only the render code differs). Live checks (round 1, round 100,
rev2), the service and distribution checks pass. Busiest stretch: main
program 26.4k -> 23.2k clocks a frame; idle 39.4% -> 42.8%; busy per
frame median 66.7%, 90th percentile 81.2%, max 91.0%. The rest of the
main program's work is game logic spread over many routines.

Second pass, same method:

| Change | Before (clocks a frame) |
|---|---:|
| 134Ch (0.4 calls): the distance test of 8 objects runs natively until the first object nearer than 10, which continues in the original code at 1393h (CF in the returned flags; three times in 7200 frames of scripted play) | 937 |
| 0A52h, in the IRQ: 05h to 12 bytes from 9825h | 571 |
| 0D54h (2 calls): a 3-byte copy | 335 |
| The idle loop's sled (`SLEDS`): 256 bytes 18h, read from any byte as JR +26, then 25 NOPs and the JP; the NOP sled ran about 220 NOPs each pass | about 860 |

Main program in the busiest stretch: 23.1k -> 21.1k clocks a frame (26.4k
before the first pass); idle 45.8% -> 47.4%; busy per frame median 61.8%,
90th percentile 75.8%, max 87.4%. The three routines leave the video

## Alignment screen

As in the sister port, the game starts with an alignment screen
(`src/m03/align.inc`), about 5 seconds (`ALIGN_FRAMES`, 300 VRTCs, restarted
by every key; RETURN or SPACE ends it). It shows white outlines of the
288x224 game picture with ticks every 8 lines (longer every 32) and, while
the picture is not moved sideways, of the whole 320x224 raster for the
monitor's automatic adjustment. Keypad 8 2 4 6 or the cursor keys move the
picture in the game's orientation: game up/down by 8 raster dots (at most
16), game left/right by one line (at most 8).

The position is a signed DSA offset applied to both screens: FB0 with the
front page at every presentation (`live_front_dsa`) and FB1 for G1, modulo
each screen's 128 KiB region. For this, GVRAM keeps blank margins of eight
lines plus eight bytes after front A (front B moved from 08C00h to 09100h),
after front B, after G1 (the tile cache moved to 29200h), and at 1FB00h and
3FB00h, where a negative DSA wraps. The outlines are drawn on G1 with its
colour 1 white meanwhile; G1 is then cleared and the palette entry
restored. Scripted test runs (`--auto`) skip the screen; `--align-frames N`
sets its length and `--test-align X Y` (test only) presets a position.

Checked in vaeg with scripted keys: the outlines, the raster outline hidden
once moved sideways, the 5 s restart, and the game shown 8 dots left and 3
lines down after game up once and game left three times. On a VA or VA2
the sister port's DSA method passed; this port's two-screen variant (FB1
DSA nonzero) has not been tried on hardware.

## F10 service screen

As in the sister port, F10 pauses the game and opens a service screen
(`src/m03/service.inc`, on by default in `build_m03.py`):

- Items: COIN A, COIN B, LIVES, BONUS, LEVEL, CONTINUE, DEMO SND (the DIP
  switches the board defines, in MAME's bit layout; the bonus names follow
  the 5-lives table when LIVES is 5), SOUND (SSG / FM, run-time switch when
  FM voices exist), TEST (20 sounds) and ROUND (debug: 0 = OFF, 1-255;
  4 6 change by one, RETURN or SPACE adds 10). With ROUND set, the round
  counters 840Dh/840Eh are preset to ROUND - 1 whenever the main program
  has cleared them (a game start), as the build-time `--test-round`, which
  now just sets its initial value. Kept across DIP restarts.
- FPS (60 / 30): the render period at run time (`live_render_period`,
  initially `L_RENDER_PERIOD`). 60 attempts a render every scheduler frame;
  a render still waits for the previous page to be shown, so the rate is
  what the machine allows. 60 is the default since the maintainer saw 60
  frames a second on a PC-88VA (2026-10-19), after the native sound driver
  and the Y-flip cache. Items now start at row 5
  so that eleven fit above the help lines.
- Keys: cursor keys or keypad 8 2 select, 4 6 change, RETURN or SPACE plays
  the test sound, F10 returns. A held direction repeats after 20 frames,
  then every 2 frames (ROUND 1 to 100 in about 3.5 s); checked in vaeg
  with held keys (`@hold`). Switch changes restart the programs on return
  (Z80 RAM cleared as at power-on, custom I/O state reset, main at 0000h);
  they are not saved. Cabinet and freeze switches are not offered.
- While the screen is open the main and sub programs get no time and no
  interrupts; the sound program runs only during the test.
- Drawn by the native renderer from a made-up video state: the game's own
  font in the game's orientation, blank background bank, no sprites. The
  selected item uses the font's second colour.
- Sound test: clear the 32 request flags at 9A80h, set the chosen one, let
  only the sound program run. In attract the sound program drops requests
  while 8657h is nonzero (measured on the reference emulator by forcing
  values), so the test clears it; F10 restores it and the saved requests.
  Requests 0-18 and 20 produced voices there; the rest did not and are not
  offered.

The FM backend and its method (fit or quick) are now run-time bytes, so one
build can switch between SSG and FM. `m03_silence` silences all voices and
forces the next update to rewrite every register; it is used on open,
close, test changes, backend switches and restarts.

`tools/check_service.py --audio MODE` drives the screen with test keys
(TEST_KEYS build: M = F10, P = play, U D L R) and checks: screen text from
the exported tile RAM, highlight, composition against the host renderer,
LIVES/BONUS changes, the sound test's register targets in SSG and FM, the
backend switch, and the restart (the boot RAM test's fill pattern, then
attract). Passes for SSG, FM-quick and FM-fit. During the restarted boot
RAM test the main program does not yield, so the picture is not updated
until it reaches attract; this is the same as at power-on.

## Pitch: an octave lower

The YM2203 plays F-number x 2^(block-1) x 55466 / 2^20 Hz (3993600 / 72)
and an SSG period TP as 3993600 / (32 TP) Hz (vaeg's np2: 125000 / TP;
ymfm; the PC-88's usual tone tables), as found in the Pengo port. The
formulas taken over from the first M03 work assumed half of both, so FM
and SSG sounded an octave above the board (the WSG plays 96000 x F / 2^20
Hz). Now TP = 1363148 / F (clamped to 4095 below F = 333) and the
F-number F x 45 / 26 (fitted voices; F x 443 / 256 for the quick ones).
`check_sound_math.py` checks the guest routines against these on every
20-bit F, `check_sound.py` the register targets. The fitted voices no
longer use MUL 0 (x 0.5): such an operator makes the tone's period two of
the model's periods, and the model does not see the octave below it adds
(heard in the Pengo port on ymfm). The voices' cache key is DDFM-3.

## Pictures while a program waits in its own loop

The picture is drawn when every program has finished its frame. At a
high score the main program requests the tune at 9A82h and waits for the
sound to clear it in a loop of its own (3545h-355Bh, rev1), so for about
1000 frames no picture was drawn: the screen kept the game-over picture through the
congratulations and the initials, and a key (ending the wait) seemed to
be needed. The boot RAM test did the same. The scheduler now draws at a
frame's start when RENDER_STARVE (2) frames have passed without a
picture, with at most BG_MIN_ROWS background rows in such a render
(`live_forced`), so that the waiting program keeps most of its time.
`--test-score` (tests) keeps player 1's score at 50000 or more: in vaeg
the course is then the game-over message, the high-score screen with the
score, the initials entry, the continue countdown and attract, as the reference emulator
shows; `check_live.py --test-score` passes through it. Round 100's
busiest stretch keeps full speed (game frames per VRTC 1.0000).
`check_service.py` follows the restart's boot over 16 samples, as the
pictures now go on through it.

### Background rows in turn; FM voices without noise

The forced renders draw at most BG_MIN_ROWS background rows, and the walk
started at row 0 each time: on the high-score screen text near the
top changes every frame, so those rows took every render's quota and the
rows below (the left half on the turned monitor) kept the game's picture.
The walk now starts after the row where the last one stopped and goes
round all 28 (`n_start_row`, `n_walked`): the screen is complete about 30
frames after the game-over message (vaeg, `--test-score`).

Fitted FM voices sounded noisy in some sounds (SOUND 08 and 19 of the
test). Played by ymfm at the game's pitches, voices with strong feedback
or high MULs had up to 81% of their power away from their harmonics: the
model renders 256 samples a period, the chip 55466 a second, so at 1.7
kHz only 33, where such feedback does not settle into a period and
sidebands above its Nyquist frequency fold back. `fmfit.py` (VERSION 4)
now renders every candidate channel at the chip's rate at pitches over
its range (50-576 Hz for the low voices, 600-4300 Hz for the high ones;
the game's sounds lie within 47 Hz-4.3 kHz) and keeps the best voice with
at most 1% of its power away from the harmonics; with none clean it
falls back to the fundamental alone (waveform 1's high voice, 93%
fundamental). All 16 voices measure 0.8% or less in ymfm at 60-4000 Hz.
The cache key includes fmfit's VERSION.

## Load display (F9)

As in the sister ports (`src/m03/diag.inc`; the layout of the Pengo
port's): F9 toggles the display in G1's margins, read upwards like the
game's text. Left, over the last 60 VRTCs, each after its letter: F game
frames (60 at full speed), D VRTCs dropped (beyond `FRAME_DEBT`, counted
in `g_sched`), R new pictures, T sound ticks (120), I idle time in
percent. The idle percentage is the idle loop's passes over those of
empty VRTCs, counted at start (`idle_calib`), so it is right on either
machine without a clock constant. Right, in hex: K the keys (K_* bits),
M the 51xx mode and remap flag, S the sound state (bit 0 chip timed out,
1 FM voices loaded, 2 FM in use). The font's digits are tile codes
10h-19h, A-Z 1Ah-33h. G1 is not paged, so the margins are drawn once a
second by the render and cleared when the display is turned off. F9 is
sampled at every VRTC with the service keys. `--diag` (tests) starts with
the display on. In vaeg, round 100's busiest stretch: F060 D000 R060 T120
I033.

For room, the sprite images' opaque boxes (1 KiB) moved from the code
area to 3800:4000h; the rectangle-list builds limit the SGP batch to
3A00:1000h, as the three-front builds already did, so that it cannot
reach the lists' areas above it. Checked: the 60-state round-100 replay
(pixel-identical, 65.7k clocks a render), live checks at rounds 1 and
100 and rev2, the service and distribution checks; the display itself in
vaeg with F9 (attract: 60 120 15 72; play: 60 120 35 58).

## Distribution

`docs/DIST.md`: the dd-pc88va ROM-less boot disk, `install_roms.py` (checks
