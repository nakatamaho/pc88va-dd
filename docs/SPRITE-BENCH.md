# Sprite benchmark (CPU, SGP and both)

How fast can sprites be drawn on the PC-88VA and PC-88VA2 by the CPU, by
the SGP, and by both at once? `SPRBENCH.COM` measures it.

```
python3 -I tools/build_sprbench.py            # build/sprbench.d88
python3 -I tools/check_sprbench.py --vaeg EXE --bios DIR [--model va|va2]
```

The disk is MS-DOS 4.0 with `SPRBENCH.COM` (`src/bench/sprbench.asm`;
font and palette from `tools/sgpbench.py`, the images generated by the
program). No ROM data. 15 kHz, memory to 5000h; it copies itself to
3000:0000, runs about 6 minutes and never returns (restart the machine).

## What is drawn

Transparent square sprites (pixel 0 transparent; synthetic images with
about one pixel in eleven transparent), sizes 16, 32, 64 and 128 dots:

- 16 colours (4 bpp): the game's mode, two packed screens, sprites on G0
  front B (GVRAM 09100h), 224 lines.
- 256 colours (8 bpp): one screen, lines 0-203 used (the CPU stays in one
  64 KiB segment).

32, 16, 8 and 4 sprites a repetition for the four sizes, at fixed
word-aligned positions (overlapping). Five ways (columns):

| Column | Drawing |
|---|---|
| CPU | CPU only: per word `LODSW` (mask), `AND [ES:DI]`, `OR [SI]` (data), `STOSW`; images pre-shifted, so word-aligned X (any X costs the same with shifted copies) |
| SGP25, SGP50, SGP75 | that share of the sprites in one SGP list, started first; the CPU draws the rest meanwhile; then the wait for the SGP |
| SGP | SGP only: per sprite SET_SOURCE, SET_DESTINATION, BITBLT 0105h from main RAM (40000h), as the game |

## Timing (BENCH 2)

Each test runs twice, each run for 240 VRTCs from a VRTC edge. When the
last repetition ends, a spin loop counts up to the next edge; the run's
time is the VRTCs to that edge minus the counted rest of the last VRTC,
converted with the spins in a whole VRTC (calibrated after each mode
change, mean of 16 VRTCs; the same loop). So the time is not rounded to a
VRTC (BENCH 1 dropped up to one VRTC: its times were 0.3-0.8% short). A
VRTC is taken as 16683.4 us (59.94 Hz); the absolute values depend on that
constant, the ratios do not. The table shows microseconds a sprite, the
mean of the two runs; the line "2 RUNS: LARGEST DIFFERENCE" shows the
largest difference between the runs over all 40 tests (red above 0.5 %). Before each size and
depth one sprite is drawn by the SGP and one by the CPU over the same
pattern and compared: `CHECK SGP=CPU` shows OK or the differing bytes.
Results also at GVRAM 12400h (`SPRB`) for the checker, which adds pixel
rates and "best/ideal": the best column against the ideal of the CPU and
the SGP fully in parallel at the best share (cpu x sgp / (cpu + sgp)).
